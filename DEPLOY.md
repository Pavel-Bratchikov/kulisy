# Развёртывание «Кулис» на сервере

Инструкция для администратора сервера. Приложение запускается через Docker Compose: PostgreSQL, Django/Gunicorn, почтовый процесс и Caddy. Python и PostgreSQL на хосте вручную устанавливать не требуется; Python 3 нужен только для создания конфигурации.

## Перед началом

Подготовьте Linux-сервер с Docker Engine и плагином Docker Compose, Python 3, доступом в интернет и местом для базы, фотографий чеков и резервных копий. Ориентир по ресурсам — 2 vCPU и 4 ГБ памяти. По архитектуре проекта сервер и резервные копии должны находиться в России.

Потребуются домен, указывающий на сервер, и параметры SMTP для отправки билетов: адрес сервера, порт, логин, пароль приложения и подтверждённый адрес отправителя. Проверьте, заняты ли порты 80 и 443 другим сайтом. Если заняты, используйте вариант с существующим прокси ниже.

Получите архив `kulisy-server.tar.gz` с исходниками. В нём нет рабочих данных и файла `.env`.

## 1. Разместить файлы и создать настройки

```bash
mkdir -p ~/apps
cd ~/apps
tar -xzf /path/to/kulisy-server.tar.gz
cd kulisy
python3 scripts/init_env.py kulisy.example.ru
nano .env
```

Замените `kulisy.example.ru` своим доменом. Скрипт создаёт `.env` с правами `600`, подставляет домен и генерирует отдельные секреты приложения и базы. Он не перезаписывает существующий файл.

В `.env` заполните SMTP-параметры вашего провайдера:

```dotenv
EMAIL_HOST=smtp.example.ru
EMAIL_PORT=587
EMAIL_USE_TLS=1
EMAIL_USE_SSL=0
EMAIL_HOST_USER=tickets@example.ru
EMAIL_HOST_PASSWORD='password-from-mail-provider'
DEFAULT_FROM_EMAIL='Кулисы <tickets@example.ru>'
```

Для SMTP на порту 465 обычно нужны `EMAIL_USE_TLS=0` и `EMAIL_USE_SSL=1`. Режимы TLS и SSL нельзя включать одновременно. Сохраните `DEBUG=0`. Не передавайте `.env` вместе с исходниками. Сохраните его закрытую резервную копию: изменение `POSTGRES_PASSWORD` в уже запущенной базе требует отдельной смены пароля внутри PostgreSQL.

По умолчанию чеки лежат в постоянном Docker-томе. Если используется приватное S3-совместимое хранилище в России, заполните переменные `S3_*` из `.env.example` и запретите публичное чтение файлов.

## 2А. Сервер без других сайтов на портах 80 и 443

Настройте DNS: A-запись домена должна указывать на IPv4 сервера; если есть AAAA-запись, она должна указывать на его IPv6. Откройте входящие TCP-порты 80 и 443 в firewall и панели провайдера. Затем выполните:

```bash
./scripts/deploy.sh
```

Скрипт проверит настройки, соберёт образ, поднимет контейнеры, применит миграции и соберёт статические файлы. Caddy выдаст и будет обновлять HTTPS-сертификат при корректных DNS и доступности портов — [условия Caddy](https://caddyserver.com/docs/automatic-https#overview). Первая сборка может занять несколько минут.

## 2Б. На сервере уже работает Nginx или Caddy

Нужен Docker Compose версии **2.24.4 или новее**. Добавьте в `.env`:

```dotenv
COMPOSE_FILE=compose.yaml:compose.proxy.yaml
```

После этого выполните `./scripts/deploy.sh`. Приложение станет доступно только на `127.0.0.1:8088`. Внешний прокси должен обслуживать домен по HTTPS и передавать запросы на этот адрес. Не открывайте порт 8088 наружу.

Пример для Caddy, работающего **на хосте**:

```caddyfile
kulisy.example.ru {
    reverse_proxy 127.0.0.1:8088
}
```

Пример для существующего HTTPS `server` в Nginx **на хосте**:

```nginx
location / {
    proxy_pass http://127.0.0.1:8088;
    proxy_set_header Host $host;
    proxy_set_header X-Forwarded-Proto https;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    client_max_body_size 12m;
}
```

HTTPS-сертификат и переход с HTTP на HTTPS в этом варианте настраиваются во внешнем прокси. Если он тоже работает в Docker, `127.0.0.1` внутри его контейнера означает другой контейнер: подключите прокси к сети приложения и направьте запросы на `caddy:80`, либо настройте другой безопасный маршрут к хосту.

## 3. Проверить запуск

```bash
docker compose ps
curl --fail https://kulisy.example.ru/health/
docker compose exec web python manage.py check --deploy
```

В ответ на `/health/` должно прийти `{"status":"ok"}`. Этот запрос проверяет Django и подключение к базе. Затем откройте сайт и проверьте: регистрацию организатора, создание мероприятия, оформление билета и доставку письма, работу камеры на телефоне по HTTPS, синхронизацию сканера после обрыва сети, загрузку/скачивание фото чека и Excel-отчёт.

Отдельная проверка SMTP на собственный адрес:

```bash
docker compose exec web python manage.py sendtestemail your-address@example.ru
```

При необходимости создайте технического администратора:

```bash
docker compose exec web python manage.py createsuperuser
```

В качестве имени пользователя укажите email в нижнем регистре. Для обычного организатора достаточно регистрации через сайт. Демоданные на рабочий сервер не загружайте.

## Резервные копии и обновления

Настройте ежедневный запуск `scripts/backup.sh`. Он сохраняет дамп PostgreSQL и архив чеков из локального тома в `backups/`. Храните копии также вне сервера, в российском хранилище; отдельно сохраните `.env`. Если чеки находятся в S3, настройте резервирование/версионирование этого bucket. Следите за свободным местом: старые локальные копии автоматически не удаляются.

Пример записи в cron с заменой пользователя и пути:

```cron
0 3 * * * cd /home/USER/apps/kulisy && ./scripts/backup.sh >> backup.log 2>&1
```

Перед ручным обновлением выполните `./scripts/backup.sh`, затем замените файлы приложения новой версией, сохранив `.env` и постоянный путь к каталогу проекта, и запустите `./scripts/deploy.sh`. Постоянные Docker-тома сохранят базу и файлы. Не меняйте имя Compose-проекта или каталога при обновлениях. После изменения кода возможен короткий перерыв в работе.

Для остановки без удаления данных:

```bash
docker compose down
```

Не добавляйте к этой команде `-v`: она удалит тома с базой, локальными чеками и сертификатами. Восстановление сначала отрабатывайте на отдельной пустой базе; откат исходников сам по себе не отменяет миграции базы.

## Если запуск не удался

```bash
docker compose logs --tail=100 web mail caddy db
```

- Порт 80/443 занят: используйте вариант 2Б.
- Сертификат не выдан: проверьте DNS, firewall и журналы Caddy.
- Ответ 400: проверьте `DOMAIN` и `ALLOWED_HOSTS` в `.env`.
- Ответ 403 при отправке формы: проверьте HTTPS, `CSRF_TRUSTED_ORIGINS` и передачу заголовка Host через внешний прокси.
- Письмо не пришло: проверьте `mail`, SMTP, режим TLS/SSL, разрешённый адрес отправителя и записи SPF/DKIM.
- PostgreSQL не принимает пароль после редактирования `.env`: верните прежний пароль или согласованно измените его в самой базе. Не удаляйте том с данными.
