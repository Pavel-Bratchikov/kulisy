# Кулисы

Веб-сервис для организации мероприятий: регистрация → QR-билет → вход с телефона → смета → Excel. Реализован как Django-монолит с серверными шаблонами и обычным JavaScript.

Развёртывание на сервере описано в [DEPLOY.md](DEPLOY.md). Архив без локальных данных создаётся командой `python3 scripts/package_server.py`. Проверка и автоматическое обновление настроены в `.github/workflows/ci-deploy.yml`.

## Быстрый запуск

Требуется Python 3.12+ (проверено локально на Python 3.14). Для разработки без Docker используется SQLite. PostgreSQL обязателен для многопользовательского развёртывания: SQLite не обеспечивает требуемые блокировки строк.

```bash
python3 -m venv .venv
.venv/bin/python -m pip install --no-user -r requirements.txt
DEBUG=1 .venv/bin/python manage.py migrate
DEBUG=1 DEMO_PASSWORD='Kulisy-demo-2026!' .venv/bin/python manage.py seed_demo
./scripts/dev.sh
```

Открыть **http://127.0.0.1:8000/**. 

Демонстрационные аккаунты, пароль для всех: `Kulisy-demo-2026!`:

| Почта | Роль |
| --- | --- |
| organizer@kulisy.test | Организатор |
| controller@kulisy.test | Контролёр |
| treasurer@kulisy.test | Казначей |

Команда `seed_demo` повторно данные не создаёт и пароли существующих аккаунтов не меняет. Работает только при `DEBUG=1`. Демоданные вымышленные; письма для них не ставятся в очередь.

Можно создать собственный аккаунт на `/accounts/signup/`. В тарифе «Старт» действует лимит одного неархивного мероприятия, 100 активных билетов и трёх участников команды. Владелец входит в командный лимит. Платежи и платные подписки в MVP не подключены. Excel доступен в MVP всем организаторам и казначеям; платный тариф из бизнес-гипотезы не используется как ограничение этой функции.

## Реализованные сценарии

- Вход по почте и паролю, создание и редактирование мероприятия, публикация/закрытие регистрации, архивирование.
- Категории билетов с лимитами. Общий лимит события и лимит категории проверяются внутри одной транзакции с `select_for_update()`.
- Публичная регистрация с согласием; телефон появляется только при включённой настройке. Один активный билет на почту для каждого события.
- UUID в QR без контактов; страница билета, печать/сохранение PDF средствами браузера. Ручная выдача и аннулирование до прохода.
- Постоянная очередь писем с QR-вложением, повторные попытки с увеличивающимся интервалом. Билет появляется сразу, независимо от SMTP.
- Приглашения по ссылке, привязанные к почте и действующие семь дней. Отзыв приглашения, удаление участника. Активные приглашения резервируют места команды.
- Сканирование камерой через html5-qrcode; поиск по имени и полному UUID; IndexedDB для списка, локальных отметок и исходящей очереди.
- Service Worker сохраняет подготовленную страницу сканера и её локальные ресурсы для перезагрузки без сети. Сам список гостей хранится в IndexedDB, а не в общем HTTP-кэше.
- Синхронизация каждые 15 секунд и при возвращении сети, идемпотентность по ID попытки. Один CheckIn на билет; повторные попытки сохраняются отдельно и видны в отчёте.
- Счётчики, графики регистраций по дням и прихода по 15 минутам, сводка по категориям.
- Статьи сметы, денежные суммы Decimal, расходы с датой и фотографией чека, остаток и превышения. Доступ к чекам только через проверку роли.
- Excel с листами «Итоги», «Категории», «Смета», «Расходы», «Конфликты». Пользовательский текст записывается как текст, а не как формула.
- Журнал доступа к спискам, билетам, снимку сканера, выгрузкам и основных изменений.

## Роли

| Действие | Организатор | Казначей | Контролёр |
| --- | --- | --- | --- |
| Настройки, категории, команда | Да | Нет | Нет |
| Список гостей и контакты | Да | Нет | Нет |
| Сканер: имя, категория, UUID, статус | Да | Нет | Да |
| Смета и чеки | Да | Да | Нет |
| Агрегаты и Excel без контактов | Да | Да | Нет |

Права проверяются на сервере для каждого события, включая API и скачивание файлов. Администратор Django — отдельная привилегированная техническая роль; доступ в `/admin/` нужно выдавать только доверенному обслуживающему персоналу.

## Офлайн-сканер

1. Войдите с телефоном контролёра и откройте сканер при работающем интернете.
2. Дождитесь загрузки списка и подготовки офлайн-страницы. Разрешите доступ к камере по кнопке.
3. При обрыве сети не выходите из аккаунта. Проходы сохраняются в IndexedDB; очередь показывается на экране.
4. При возвращении сети нажмите «Обновить и синхронизировать» или дождитесь автоматической отправки.
5. Перед окончанием смены убедитесь, что очередь равна нулю. Затем удалите данные с телефона кнопкой на странице сканера.

Список и офлайн-страница действуют 24 часа после загрузки. Сервер принимает отметки за последние семь дней с допуском часов устройства до пяти минут вперёд. Серверные времена и время устройства хранятся отдельно. Считается **первый проход, полученный сервером**, а не наименьшее время телефона: часы устройств нельзя считать доверенными. Повторная отправка той же попытки не создаёт конфликт.

Без сети невозможно предотвратить проход по одному билету на двух независимых телефонах или немедленно узнать об аннулировании билета/отзыве доступа. Сервер обнаружит это при синхронизации. Новые регистрации появляются после обновления списка. После отказа в доступе сканер блокируется, удаляет список имён и сохраняет неотправленные отметки; восстановить доступ может организатор. Выход из аккаунта удаляет локальные данные после предупреждения.

Камере нужен HTTPS или localhost. Адрес вида `http://192.168...` для телефона не подходит. Физические Android/iPhone, автофокус, плохое освещение и скорость потока нужно проверить на площадке. Автотест не подтверждает целевые 3 секунды или пропускную способность 300 гостей за 8 минут.

## Почта

Локально используется консольный backend. Для обработки очереди во втором терминале:

```bash
DEBUG=1 .venv/bin/python manage.py send_ticket_emails --loop
```

Без `--loop` команда обрабатывает одну порцию до 100 писем. В production работает отдельный сервис `mail`. Настройте SMTP, `PUBLIC_BASE_URL`, адрес отправителя и записи SPF/DKIM у своего провайдера. При успешной отправке письмо исключается из очереди. При аварии между передачей письма SMTP и фиксацией результата возможна повторная доставка: гарантировать exactly-once на границе SMTP нельзя.

## Развёртывание

Контейнеры: Caddy → Gunicorn/Django → PostgreSQL, плюс почтовый worker. Приложение запускается без root, PostgreSQL не публикует порт наружу, HTTPS предоставляет Caddy. JavaScript-библиотеки и стили локальные: посетители не обращаются к CDN.

1. Подготовьте сервер в России, домен с A/AAAA-записью на него и открытые порты 80/443.
2. Скопируйте `.env.example` в `.env`, заполните домен, SMTP и уникальные секреты. `SECRET_KEY` должен содержать не менее 50 случайных символов. `DEBUG=0`.
3. Для чеков настройте приватный S3-совместимый bucket в России (`S3_*`). Без S3 файлы сохраняются в именованном томе `media_data`; скрипт `scripts/backup.sh` включает его в отдельный архив чеков.
4. Запустите:

```bash
docker compose up -d --build
docker compose exec web python manage.py createsuperuser
docker compose exec web python manage.py check --deploy
docker compose logs --tail=100 web mail
```

`.env` автоматически читает Docker Compose. Django при обычном запуске файл `.env` не загружает — передавайте переменные окружения явно. `TIME_ZONE` по умолчанию `Asia/Novosibirsk`, даты хранятся с часовым поясом; для другой площадки измените настройку.

Реальный домен, сервер, SMTP и хранилище не подключались: эти реквизиты в исходных документах отсутствуют. Наличие настроек размещения и согласия не означает юридическую проверку или автоматическое соответствие требованиям обработки ПДн. Перед публичным запуском организатор должен заполнить свои реквизиты, утвердить текст согласия и сроки хранения, настроить удаление по обращениям и правила доступа к резервным копиям.

## Резервные копии

`scripts/backup.sh` создаёт PostgreSQL custom dump и архив локальных чеков с закрытыми правами. Настройте ежедневный cron на сервере. Для загрузки в российское объектное хранилище нужны AWS CLI и переменные `BACKUP_S3_URI`, `S3_ENDPOINT_URL`, стандартные AWS credentials. При отсутствии `BACKUP_S3_URI` копия остаётся локальной. Назначьте политику хранения bucket и включите версионирование чеков; скрипт не удаляет старые копии.

Проверка восстановления на **отдельной пустой базе**, не на рабочей:

```bash
pg_restore --no-owner --dbname=postgresql://USER:PASSWORD@HOST/EMPTY_RESTORE_DB backups/kulisy-TIMESTAMP.dump
```

Секреты в реальной эксплуатации передавайте через защищённый конфиг/libpq, а не историю команд. Резервные копии и фото чеков не включаются в исходники.

## Проверки

```bash
DEBUG=1 .venv/bin/python manage.py test
DEBUG=1 .venv/bin/python manage.py makemigrations --check --dry-run
```

Тесты покрывают права на уровне событий, согласие, лимиты, аннулирование, идемпотентность синхронизации, конфликты, очередь писем, приглашения, CSRF, файлы и Excel. Конкурентный тест последнего места запускается только на PostgreSQL; на SQLite он явно пропускается. Для PostgreSQL передайте `POSTGRES_HOST`, `POSTGRES_PORT`, `POSTGRES_DB`, `POSTGRES_USER`, `POSTGRES_PASSWORD`; тестовый пользователь БД должен иметь право создавать отдельную тестовую базу.

Сценарий проверки перед пилотом: 30 билетов, три устройства, повтор одного билета на двух устройствах без сети, восстановление связи, сверка CheckIn и листа «Конфликты», плохой свет, отказ камеры, отсутствие SMTP, превышение сметы, скачивание и проверка Excel. Сначала проведите это на тестовых данных.

## Структура

- `events/` — события, категории, роли, приглашения, аудит.
- `tickets/` — регистрация, билеты, QR, почтовая очередь.
- `scanning/` — снимок списка, проверка очереди, уникальный проход и конфликты.
- `budget/` — смета, расходы, защищённое скачивание чеков.
- `reporting/` — агрегаты, графики и Excel.
- `templates/`, `static/` — адаптивный интерфейс и офлайн-клиент.
- `config/`, `compose.yaml`, `Caddyfile`, `scripts/` — запуск и эксплуатация.

Онлайн-оплата, задачи команды, рассылки, боты и тарифный биллинг оставлены за границами MVP согласно архитектуре.

### Результат проверки реализации

- 33 серверных теста успешно выполнены на PostgreSQL 16, включая конкурентные регистрации и проходы.
- На SQLite: 31 тест успешен, 2 проверки блокировок PostgreSQL ожидаемо пропущены.
- `manage.py check --deploy` — без замечаний с production-настройками и тестовым секретом.
- Docker-образ собран с нуля; локально проверен полный Compose-комплект с PostgreSQL, Gunicorn, почтовым worker и Caddy, включая миграции, статику и резервные копии. На внешнем сервере с реальным доменом и SMTP ещё не запускался.
- Chromium/Playwright: вход, страницы кабинета, Excel, мобильная регистрация, офлайн-проход, повтор, перезагрузка без сети и синхронизация успешно проверены. Скриншоты и тестовая выгрузка — в локальной папке `artifacts/` (не входят в Git/Docker).
- Физическая камера телефона, реальный SMTP и S3 требуют проверки с реквизитами развёртывания.

Браузерную проверку можно воспроизвести после запуска сервера с демоданными:

```bash
.venv/bin/python -m pip install --no-user -r requirements-dev.txt
PLAYWRIGHT_BROWSERS_PATH=/tmp/kulisy-browsers .venv/bin/python -m playwright install chromium --no-shell
PLAYWRIGHT_BROWSERS_PATH=/tmp/kulisy-browsers .venv/bin/python tests/browser_smoke.py
```

Этот тест отмечает одного ещё не пришедшего демогостя. Не запускайте его на рабочих мероприятиях.
